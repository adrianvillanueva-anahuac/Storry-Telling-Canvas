Database Topology (Firestore)NoSQL

Cloud Firestore database (firebaseConfig.firestoreDatabaseId) holds workspace-wide registries at the root and isolates storyboard scene data under each project document.

/users/{uid}                  ← User profile, global role, lastLoginAt
/admins/{uid}                 ← Admin privilege marker checked by rules
/invites/{email}              ← Pre-authorized email + pending role
/images/{imageId}             ← Metadata + Vercel Blob URLs (no base64)
/globalVideos/{videoId}       ← Shared YouTube video references
/projects/{projectId}         ← title, description, ownerId, status, participants{}
  ├─ /nodes/{nodeId}          ← Active scene cards, pins[], drawings[]
  ├─ /storedNodes/{nodeId}    ← Archived scene cards + storeNote
  ├─ /connections/{connId}    ← Port-to-port SVG lines & labels
  └─ /texts/{textId}          ← Floating text, sticky notes, group containers

Per-Project Participants MapRBAC

Every project document stores an email-keyed participants map (lowercase email keys) so assignments work both before and after a user's first Google Sign-In.

project.participants = {
  "artist@studio.com": {
    email: "artist@studio.com",
    role: "Editor",           // "Admin" | "Editor" | "Viewer"
    uid: "firebase-uid",
    name: "Artist",
    assignedAt: "ISO-8601"
  }
}

Rule Note: Only global Admins can modify the participants map on /projects/{projectId}. Editors can update project canvas subcollections cleanly.

Permission Resolution OrderRuntime + Rules

Both src/App.tsx and firestore.rules follow the exact same hierarchy:

  • 1. Super User (adrian.byakko@gmail.com): Always global Admin, sees all projects, cannot be deleted or demoted, and can permanently delete workspace user records.
  • 2. Global Admin (/admins/{uid} or users.role == 'Admin'): Full access to Admin Console, all projects, invites, and project participants.
  • 3. Project Participant Role: For non-admins, effectiveRole comes from project.participants[email].role — so a global Viewer assigned as Editor on Project A can edit Project A while staying read-only elsewhere.
  • 4. Legacy Fallback: Projects with no participants map remain readable, using the user's global role.

Why Vercel + Firebase Split ExistsInfra

This app uses a deliberate hybrid cloud split that keeps costs low and avoids permission issues:

  • Firebase handles Google Sign-In (Auth) and real-time collaborative state (Firestore + firestore.rules).
  • Vercel serves the compiled React SPA (dist/), hosts Serverless API endpoints (api/blob-token.ts, api/blob-delete.ts), and stores binary images in Vercel Blob (visual-workflow-media).
  • Legacy Disk Images live in public/uploads/ so historical /uploads/... links keep loading cleanly without touching Firestore URLs.

Recipe 1: Add a New Field to Scene NodesData Model

  • 1. Add the property to WorkflowNode in src/types/workflow.ts.
  • 2. Add default value in handleAddNode() inside src/App.tsx and in createProject() inside src/services/firestoreService.ts.
  • 3. Render/edit it in WorkflowNodeCard.tsx or NodeDashboardModal.tsx using onUpdateNode(id, { ... }).
  • 4. If it needs server-side validation, update isValidNode() in firestore.rules and redeploy rules.

Recipe 2: Add a New Modal or Canvas ToolUI

  • 1. Create component in src/components/modals/MyModal.tsx (always honor isReadOnly for Viewers).
  • 2. Add open/close state in src/App.tsx near lines 125–155.
  • 3. Add trigger button in src/components/Header.tsx (or inside NodeDashboardModal.tsx).
  • 4. Use setDoc(..., { merge: true }) via firestoreService.ts—never put raw base64 images inside Firestore docs.

Recipe 3: Change Security Rules or RolesSecurity

  • 1. Edit firestore.rules and keep firebase-blueprint.json documented in sync.
  • 2. Keep UI checks in src/App.tsx (effectiveRole, visibleProjects) matching rule helpers (canEditProject, canReadProject).
  • 3. Deploy updated rules to Firebase before pushing frontend changes that depend on them.
  • 4. Remember: client SDK cannot delete Firebase Auth accounts—deleteUserCompletely wipes Firestore workspace/project access immediately.

Recipe 4: Deploy Changes to ProductionDeploy

  • 1. Verify TypeScript & Vite bundle cleanly: npm run lint and npm run build.
  • 2. Deploy Vercel production build: npx vercel --prod --yes (uses vercel.json + BLOB_READ_WRITE_TOKEN env var).
  • 3. Never store secrets in src/ or VITE_* vars; serverless token minting lives strictly in api/blob-token.ts.
  • 4. Keep vercel.json rewrites excluding api/ and uploads/ so API JSON & static assets aren't caught by index.html.
